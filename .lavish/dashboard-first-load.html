3. Your idea, and where I push back

Strongest form of the idea

A dashboard is a scrolling grid; the user only cares about what is on screen. "Fast" means time-to-visible-content, not time-to-everything. Every off-screen request steals a scheduler slot, a server connection turn, and Pi CPU from something the user is actually looking at, and every off-screen poll is pure waste on a phone. So: visible controllable, then visible informational, then nothing else until it scrolls into view, and off-screen widgets stop polling. The scheduler already has the tiers; the PRD for it (#209) even defined normal as "visible read-only charts". It was never wired to visibility.

Where I disagree, before building on it

Viewport prioritisation would not have fixed this load. Priority in the browser only helps if the server can act on the order. With one connection, whoever grabs it first wins, and the 9 s holder is a request that no widget owns. Even a perfectly prioritised visible set would have sat behind it. So this design has to fix the server-side contention first, and treat visibility as the second win, which it is: once queries cost 15 to 150 ms, "visible first" is what turns a 600 ms load into a 200 ms one.

Never fetching off-screen widgets has a cost you will see. Scroll down and you get a skeleton plus the 350 ms minimum loader time added in #219. I suggest a prefetch margin below the fold rather than idle prefetching, which keeps your rule ("don't run queries for what isn't visible") almost intact. Decision D5.

What would make me wrong: if your dashboards fit on one screen, visibility gating is a no-op and only the backend work matters; if you routinely open dashboards with 20+ widgets on a phone, it is the bigger win of the two. Both cases are still "backend first".

D2 · THE CONNECTION

How should the database connection be shaped?

The comment on the pool says "SQLite performs best with a single writer connection". That is true of writers. WAL exists so readers never block on the writer or on each other. One handle for both throws that away. Every option below keeps exactly one writer.

Where should "which measurement types have readings" come from?

D4 · VACUUM

What replaces the two-hourly VACUUM?

Chesterton's fence: it exists so the file shrinks after retention deletes. The stats it logs show 218 free pages out of 24 880. It is doing 9 s of exclusive I/O to move 0.9%.

Mechanism in all cases: WidgetFrame owns an IntersectionObserver and publishes visibility through context; hooks consult it when scheduling and when polling. Widgets stay mounted (unmounting would lose chart state and fight react-grid-layout). This decision is only about the policy.

7. The design

Validate each section

Seven sections. Each ends with an approve-or-change control. Where a section leans on an open question in section 8, it says so.

7.1 · DATABASE HANDLES

One file, two handles, reads never wait for writes

Components

  • database.Open(cfg, logger) (*Handles, error) returns Handles{Reader, Writer *sql.DB}. Both handles open the same path with the same otelsql-instrumented driver; the pool name is an attribute so the existing db_sql_* metrics split cleanly.
  • Migrations run on the writer before the reader is handed out.
  • Every repository constructor takes *Handles. Read methods use Reader, write methods and every transaction use Writer. There is no method that takes a bare *sql.DB any more, so a read path cannot be handed the writer by accident, and a write on the reader fails loudly under query_only.
  • InitialiseDatabase and the single-connection comment go. The test harness and integration suite build Handles the same way over a temp file.

Why these settings

  • 4 readers: the Pi has 4 cores and the browser cap is 4. More readers only queue on CPU.
  • _txlock=immediate on the writer: a write transaction takes the lock at BEGIN, so it can never deadlock trying to upgrade from a read lock mid-transaction.
  • busy_timeout on both: a reader can briefly collide with a checkpoint; 5 s of patience replaces an error.
  • Checkpointing: with readers always open, SQLite's passive auto-checkpoint can fall behind and the WAL grows. The cleanup pass in 7.3 runs a wal_checkpoint(TRUNCATE) on the writer, best effort.

7.2 · WHICH SERIES EXIST

The join table becomes the truth about (sensor, type) pairs; no query ever scans readings to find out

  • Meaning change. sensor_measurement_types currently means "assigned at migration time" (every sensor got temperature, nothing since). It becomes "this sensor has reported this type at least once", plus the unit. Q4 asks you to confirm the semantics.
  • Backfill. A migration rebuilds the table from readings once: INSERT OR IGNORE … SELECT DISTINCT sensor_id, measurement_type_id FROM readings. This is the last full scan of readings the codebase performs, at migration time, on the writer, before the API is up. Rows that the old backfill added for pairs that never reported are removed by the same migration.
  • Maintenance on ingest. The readings repository keeps an in-memory set of known pairs, seeded from the table at boot. On first sight of a new pair inside the ingest transaction it inserts the row, then adds the pair to the set. Steady state cost: a map lookup per reading, zero writes. Sensor deletion already cascades.
  • Retention. When every reading of a pair ages out, the pair stays. That is the intended answer to "has this sensor ever reported humidity" for the config dialog, and it is what keeps the boot query in 7.2 honest about series it should look for.
  • Queries rewritten onto it (all indexed, all under a millisecond, all with plan tests):
    • GetAllWithReadings: measurement types joined to the pair table, not to readings. F01.
    • GetMeasurementTypesWithReadings(sensorId): same, filtered by sensor.
    • GetLatest (F05): one statement, one indexed lookup per pair instead of ranking the table:

7.3 · CLEANUP, SPACE RECLAIM, AND THE GAUGE

Every freed page is returned to the filesystem, without ever locking the whole file

How incremental vacuum reclaims everything

With auto_vacuum=INCREMENTAL, SQLite keeps pointer-map pages so it can relocate any page. PRAGMA incremental_vacuum(N) moves up to N free pages to the end of the file and truncates it. Run with no N, or in a loop until freelist_count is zero, it returns every free page. The file shrinks by exactly the bytes the deletes freed. What it does not do is defragment the pages that remain; that was the only thing the full VACUUM added, and on a table that is appended in time order and deleted in time order there is almost nothing to defragment.

The loop runs on the writer in chunks of 512 pages (2 MB) with the lock released between chunks, so ingest and readers interleave. After a normal two-hourly retention pass on your data (218 free pages) it is one chunk and a few milliseconds. After a retention change that frees a gigabyte it is a few hundred chunks over a few seconds, none of them blocking.

One-time switch. auto_vacuum can only be changed by a VACUUM. Migration 000021 sets the pragma and runs the last full VACUUM there is. On the Pi that is one 9 to 14 s pause at the next deploy, before the API listens.

The refactor, so nothing is left over

  • MaintenanceRepository loses Vacuum. It gains ReclaimFreePages(ctx, chunk) (pagesFreed int, err), Checkpoint(ctx) and keeps Optimise and DatabaseStats.
  • performDatabaseMaintenance becomes: stats → reclaim loop → optimise → checkpoint(TRUNCATE) → stats → one log line with pages_freed, bytes_reclaimed, duration_ms. The "before vacuum" and "after vacuum" log lines and their field names go.
  • The existing gauges sqlite.database.size_bytes, freelist_bytes and freelist_ratio stay and are recorded from the same pass.
  • Tests: insert then delete a block of rows on a temp database, run the pass, assert freelist_count == 0 and the file size dropped by at least the freed pages; and a second test that runs the pass concurrently with reads and asserts no read waited longer than the chunk.

The gauge you asked for

A sampler on the reader pool runs at boot and at the end of every cleanup pass: SELECT sensor_id, COUNT(*) FROM readings GROUP BY sensor_id, one index scan. It records sqlite.readings.rows as an observable gauge with a sensor attribute, and the total. The same sample feeds the reading-stats endpoint (F16) with a sampled_at field, replacing the per-sensor COUNT loop on every widget load. Q3 asks whether up-to-two-hours-old counts are acceptable for that widget.

7.5 · THE DASHBOARD CLIENT

A widget declares what it is; the frame knows where it is; one hook turns both into requests

Components

  • WidgetDefinition.kind: 'controllable' | 'informational', required. Sensor toggle is the only controllable today.
  • WidgetFrame owns one IntersectionObserver on its root and provides { visible, kind } through a WidgetContext. Widgets stay mounted; nothing is unmounted on scroll, so chart state and react-grid-layout are untouched.
  • requestScheduler.schedule(priority, fn, { signal }): an aborted waiter is removed from its queue and rejects with the abort reason. No other scheduler change.
  • useScheduledQuery(fetcher, { pollIntervalMs, deps }): the one hook that owns the state machine above, reads the widget context, registers with a single page-level PollClock (one 1 s timer; each subscriber has its own due time) instead of a setInterval per widget, and pauses on document.visibilityState. useReadingsData, the min/max/avg, heatmap, alert-summary, uptime, health-timeline, reading-stats and comparison-chart data paths all move onto it. Requests from outside the dashboard (auth, dashboards list, notifications) are not widgets and stay as they are.
  • PropertiesProvider and CurrentReadingsProvider in ProviderWrapper, each owning exactly one reconnecting socket; useProperties and useCurrentReadings read context. useProperties gains reconnection for free. The widget subtitle no longer opens anything.
  • useLoaderVisibility gains showAfterMs = 100: a load that finishes within 100 ms never shows a loader; one that does not shows it and keeps the existing 350 ms hold. No stale data is ever rendered, per your note.
  • useReadingsData merge becomes one pass over a Map<time, Map<sensor, value>> and the two JSON.stringify diffs become a fingerprint (row count, first and last time, last value per sensor). F15.

Error handling

  • A fetch that fails leaves the previous data on screen with the existing error state; the next tick retries. Nothing loops faster than the widget's interval.
  • An abort is not an error: the hook returns to held silently.
  • If IntersectionObserver is unavailable (old WebView), the frame reports visible, and behaviour equals today's.
  • A socket drop in a provider reconnects with the existing backoff; consumers see the last snapshot until then.
  • Server side, a reader that hits busy_timeout returns the same 500 as today with the error logged; with 5 s of patience it should not happen, and the trace will say if it does.

Data flow on a load, after this design

  1. Auth, then dashboards, with the shell painted throughout.
  2. Frames mount; those in the viewport or the margin report visible.
  3. Visible controllable widgets queue high, visible informational queue normal; at most 4 in flight.
  4. Each request hits a reader; the writer keeps ingesting.
  5. Responses land in 15 to 150 ms; loaders were never shown.
  6. Held widgets do nothing until scrolled to.

8. Open questions from your answers

Four
Q1 · FOLLOWS D4

Does "reclaim the full set of bytes" mean what 7.3 delivers?

7.3 returns every free page to the filesystem after every cleanup pass, so the file never carries freed space forward and can never grow from deletes. It does not rewrite live pages to defragment them, which is the one thing a full VACUUM did that incremental cannot. On this workload (append in time order, delete in time order) live pages are already contiguous, so the difference is a rounding error. If you want defragmentation as well, the only tool is a full VACUUM, and the honest design is a rare scheduled one in a quiet window on top of 7.3.

Q3 · THE GAUGE

Is a count sampled at boot and after each cleanup pass the right gauge, and may the reading-stats widget use the same sample?

An exact live count would mean a counter maintained on every insert and delete, which is bookkeeping that can drift. A COUNT(*) per sensor on each widget load is what F16 is today. The sample is exact when taken, cheap, on the reader pool, and off every request path. The stats widget would show counts up to one cleanup interval old, with the sampled time next to them.

Queued
Q4 · FOLLOWS D3

Confirm the new meaning of the sensor-to-type table

After 7.2 a row means "this sensor has reported this type at least once since the backfill", and rows survive retention. The config dialog's type list and the per-sensor type list both come from it. Sensors created through the API with a declared type set would also get rows at creation, so a sensor that has not reported yet can still be configured.

SQ4 · CORRECTS Q4

"Declared at creation" has no per-sensor source

Sensors are created with a driver and no measurement types. Drivers declare supported types, but per driver: the Zigbee driver's list is every type any Zigbee device can report, so using it would say a plug reports humidity and temperature. The HTTP temperature driver's list is exactly one type, where it would be right. The repository's assign method has no callers and there is no API for it.

SQ1 · KNOBS

Which of the new numbers should be application properties, and which stay constants?

Candidates: reader pool size (4), reclaim chunk (512 pages), session touch interval (60 s), loader show delay (100 ms), scheduler cap (4, already an env override), visibility margin (one third). The properties page you just shipped can carry any of them, and each one carried is a definition, a default, a validation rule and a restart flag to maintain.

SQ2 · THE BENCHMARK IN CI

When does the first-load benchmark run, and on what?

CI today runs unit and integration jobs on every pull request and push; the integration job starts the server in-process with mock sensors in containers. The benchmark needs a server on a seeded database, the built UI, and a browser. It does not need the compose stack: Playwright can start the built binary against a seeded temp database, and the Go server already serves the built SPA. A five-million-row seed takes tens of seconds to write and can be cached by seed version.

SQ3 · A CONTRACT CHANGE

The reading-stats response gains a sampled time. What shape?

Today GET /sensors/stats/total-readings returns a plain map of sensor name to count. Q3 adds when the counts were sampled. The generated CLI and the UI hook both consume this.

Any deadline or release constraint the spec should carry?

The design has none. Two things a date would change: whether the backend slices ship as one release or several, and whether the deploy that flips to incremental vacuum, which pauses the Pi for roughly ten to fifteen seconds at startup, needs to land at a particular time.

SPEC 1 · EXECUTIVE SUMMARY AND KPIS

1. Executive Summary

Problem statement. A dashboard's first load takes eight to nine seconds because one measurement-types query full-scans the readings table and, with a single database connection, every other request and the MQTT ingest path queue behind it. Off-screen widgets fetch and poll as if they were on screen, a two-hourly VACUUM stalls the whole application, and the boot-time readings seed takes over forty seconds cold.

Proposed solution. Split the database into a reader pool and a single writer, answer "which series exist" from a maintained join table instead of the readings table, replace VACUUM with chunked incremental reclaim, batch ingest and auth, and make the dashboard fetch only what is visible, in priority order, through one scheduled-query hook.

SPEC 2 · USER STORIES AND ACCEPTANCE CRITERIA

2. User Stories

Personas.

  • Home operator: opens a dashboard on a phone or desktop to check state or flip a switch, then leaves.
  • Dashboard author: composes dashboards from widgets and configures them through the dialog.
  • Maintainer: runs the single Raspberry Pi and SQLite deployment, watches the traces and metrics, and deploys releases.

US-1. Visible widgets populate within a second

As a home operator, I want every widget I can see to be populated within a second of opening a dashboard, so that the page is usable the moment it appears.

  • Given the reference dashboard and the seeded database, when the page is opened warm, then every frame intersecting the viewport plus one third of a viewport height below it reports data-widget-state="populated" within 1000 ms of navigation start.
  • Given the same, when the server process has just restarted, then the same frames are populated within 2000 ms.
  • Given a widget whose data arrives within 100 ms of its fetch starting, when it renders, then no loader is shown at any point.
  • Given a widget whose data takes longer than 100 ms, when the loader is shown, then it stays for at least 350 ms once shown.
  • Given the sensor toggle widget, when the page loads, then it shows the indeterminate state until the current-readings snapshot arrives and never a remembered value.
  • Given the dashboards request in flight, when the page renders, then the page shell and a neutral grid skeleton are visible rather than an empty page.

US-2. Off-screen widgets do nothing until they are seen

As a home operator, I want widgets I have not scrolled to to stay quiet, so that what I am looking at gets the device and the server to itself.

  • Given a widget whose frame lies more than one third of a viewport height below the viewport, when the dashboard loads, then no request is issued for it and no poll timer is registered for it.
  • Given a held widget, when its frame enters the viewport plus margin, then its fetch is queued at that moment.
  • Given a widget queued but not yet started, when its frame leaves the viewport plus margin, then the queued fetch is aborted and the widget returns to held without an error state.
  • Given a populated widget that left view and returns after less than its poll interval, when it re-enters, then no request is issued.
  • Given a populated widget that left view and returns after more than its poll interval, when it re-enters, then one request is issued immediately.
  • Given the tab hidden, when a widget's poll interval elapses, then no request is issued; when the tab is shown again, then visible widgets older than their interval refresh once.
  • Given twelve chart widgets with 30 s intervals on one page, when polls are due, then they are driven by one page-level timer, not twelve.

US-3. Controls first

As a home operator, I want controllable widgets to load before informational ones, so that a switch is right before a chart is pretty.

  • Given visible controllable and informational widgets queued together with the concurrency cap reached, when a slot frees, then the controllable widget's fetch is admitted before any informational one.
  • Given a command in flight, when polls come due, then no new low-priority fetch is admitted until the command settles or the existing 5 s latch expires.
  • Given the scheduler cap of four, when many widgets are visible, then no more than four dashboard read requests are in flight at once.
  • Given any dashboard widget data path, when it fetches, then the request goes through useScheduledQuery; there is no direct API call from a widget or its hook.

US-4. Configuring a widget is instant

As a dashboard author, I want the measurement-type list in the widget dialog to appear as soon as I open it, so that configuring a widget does not stall the page.

  • Given a dashboard page load, when the network is inspected, then no request for measurement types with readings has been made.
  • Given the dialog opened for the first time, when the type list is requested, then the response is served under 10 ms of server time at p99 on the seeded database and the list contains exactly the types with at least one row in the join table.
  • Given the dialog opened a second time, when it renders, then the list comes from the provider without a new request.
  • Given a comparison chart on the page, when it loads, then the plain measurement-types list is requested at most once per page however many comparison charts there are.

US-5. Reads do not wait for writes

As a maintainer, I want a slow read or a burst of ingest to cost only itself, so that one bad statement can never stall the application again.

  • Given a write transaction open on the writer, when a read is issued on the reader pool, then it returns without waiting for the transaction.
  • Given a write statement issued through the reader handle, when it executes, then it fails with SQLite's read-only error and is logged.
  • Given the process started, when db_sql_connection_max_open is observed, then it reports 1 for the writer pool and the configured reader size for the reader pool, each labelled by pool name.
  • Given database.reader.connections unset, when the server starts, then the reader pool has 4 connections; given it set to 2, then 2, after a restart; given it set to 0 or a negative value, then the property is rejected by validation.
  • Given both handles, when either meets a lock, then it waits up to 5000 ms before failing.

US-6. Freed space is returned without stalling

As a maintainer, I want retention deletes to shrink the database file every pass without stopping the application, so that the file cannot grow on a device that is rarely restarted.

  • Given rows deleted by a cleanup pass, when the pass ends, then freelist_count is zero and the file is smaller by at least the number of freed pages times the page size.
  • Given a cleanup pass reclaiming pages, when readings requests run concurrently, then none exceeds its idle latency by more than 200 ms.
  • Given a database on the previous full-vacuum configuration, when migration 000021 runs, then auto_vacuum reports incremental afterwards and the migration has performed the final full VACUUM before the API listens.
  • Given the maintenance pass, when it completes, then one log record carries pages freed, bytes reclaimed and duration, and no record mentions vacuum.
  • Given the pass, when it completes, then a truncating WAL checkpoint has been attempted on the writer and its outcome logged at debug.
  • Given the codebase, when searched, then no VACUUM statement remains outside migration 000021.

US-7. The readings store is correct before the first connection

As a maintainer, I want the boot-time seed of the latest readings to take milliseconds, so that the first dashboard after the daily restart is not the slowest of the day.

  • Given the seeded database, when the latest-per-series query runs, then EXPLAIN QUERY PLAN shows one search of idx_readings_sensor_type_time per pair and no scan of readings.
  • Given the seeded database cold, when the process starts, then the store is seeded within 500 ms and the API does not listen before it is.

US-8. Ingest is one transaction per batch

As a maintainer, I want an MQTT message to cost one transaction, so that the writer is idle most of the time.

  • Given a message with nine readings for a known sensor and known types, when it is stored, then at most 12 statements execute, inside one immediate transaction, with no name lookup statements.
  • Given a reading for a (sensor, type) pair never seen before, when it is stored, then exactly one row is inserted into the join table inside the same transaction, and a second reading for the pair inserts none.
  • Given a sensor renamed through the API, when its next reading arrives, then the name cache resolves the new name and the old name is unknown.
  • Given the threshold processor, when a message with nine readings for one sensor is processed, then the alert rules for that sensor are read once; given a rule created or edited, then the next message reads them again.
  • Given a batch where the insert fails, when the transaction rolls back, then no reading of that batch is stored and the sensor health is set to bad with the storage error, as today.

US-9. Auth is one read per request

As a maintainer, I want request authentication to cost one statement, so that it stops being the most frequent thing on the connection.

  • Given a valid session cookie, when any API request is handled, then one read joining session, user and permissions executes and no other auth statement does.
  • Given the session's last-accessed time older than 60 s, when a request is handled, then one update executes on the writer; given it younger, then none.
  • Given a session deleted, when the next request with its cookie arrives, then it is rejected; nothing is cached across requests.

US-10. One socket per page, snapshots to the newcomer

As a maintainer, I want a page to hold one properties socket and one current-readings socket, so that connecting clients do not multiply messages.

  • Given twelve widget frames on a page, when the page loads, then exactly one properties socket and at most one current-readings socket are opened.
  • Given an existing properties subscriber, when a new client connects, then the existing subscriber receives no message caused by that connect.
  • Given the properties socket dropped, when the server returns, then the client reconnects with the same backoff the current-readings socket uses today.
  • Given the sensors socket connect handler, when it queries active sensors, then the query runs on the reader pool.

US-11. Widgets ask for exactly what they show

As a home operator, I want the min/max/avg and heatmap widgets to load only their own sensor and type, so that they are not pulling a month of everything.

  • Given a min/max/avg widget configured for one sensor and one type, when it fetches, then the request carries type and sensor and the response contains only that series.
  • Given the heatmap widget, the same.
  • Given the generated API client, when a query key not in the schema is used, then the TypeScript build fails.
  • Given any API response over 1 KB, when a client accepts gzip, then the response is compressed; given a websocket upgrade or /metrics, then it is not.
  • Given any JSON API response, when inspected, then it is not indented.

US-12. Readings counts as a gauge and a sample

As a maintainer, I want the readings row count in the metrics, so that I can watch the table grow and shrink.

  • Given the process started and each cleanup pass ended, when metrics are scraped, then sqlite.readings.rows is present with one series per sensor and a total.
  • Given GET /api/sensors/stats/total-readings, when called, then the response is { sampled_at, counts } where counts maps sensor name to count and sampled_at is the time of the last sample, and no COUNT statement executes during the request.
  • Given the reading-stats widget, when it renders, then it shows the sampled time next to the counts.

US-13. The numbers are guarded

As a maintainer, I want regressions in load time and query plans caught before merge, so that this work stays done.

  • Given a pull request or push, when CI runs, then a third job builds the binary and the UI, restores or creates the seed, starts the server, and runs the Playwright benchmark, failing the build on K1, K2 or K3.
  • Given the seed, when its version is unchanged, then it is restored from cache rather than regenerated.
  • Given any query this spec touches, when the Go tests run, then a query-plan test asserts it does not scan readings.

US-14. Less to parse

As a home operator on a phone, I want the dashboard bundle to carry only what the dashboard uses.

  • Given the UI dependencies, when inspected, then react-query is not among them.
  • Given the API docs page, when the dashboard loads, then swagger-ui is not in the initial bundle and is loaded on first navigation to the docs page.

Non-goals. Stale-while-revalidate rendering; a locally cached dashboard layout; progressive time ranges; per-widget code splitting; request coalescing; caching of session validation across requests; a post-deploy check against OpenObserve; any change to the aggregation tiers or the readings query itself; rows in the join table from driver declarations.

SPEC 4 AND 5 · TECHNICAL SPECIFICATIONS AND RISKS

4. Technical Specifications

Architecture overview.

  • database.Open(cfg, logger) (*Handles, error) returns Handles{Reader, Writer *sql.DB} over one file through the otelsql-instrumented driver with a pool-name attribute. Reader: database.reader.connections open connections (default 4), query_only=1, busy_timeout(5000). Writer: one connection, _txlock=immediate, busy_timeout(5000), foreign keys on, WAL, synchronous=NORMAL. Migrations run on the writer before the reader is handed out. Every repository constructor takes *Handles; read methods use the reader, write methods and transactions the writer; no method takes a bare *sql.DB.
  • sensor_measurement_types means "this sensor has reported this type at least once". Migration 000022 rebuilds it from readings once and removes rows for pairs with no readings. The readings repository keeps an in-memory set of known pairs seeded at boot and inserts a row on first sight inside the ingest transaction. Rows survive retention and are removed only by sensor deletion.
  • Types with readings, types with readings per sensor, and latest-per-series are read from the join table; latest-per-series is one statement probing idx_readings_sensor_type_time once per pair.
  • Migration 000021 sets auto_vacuum=INCREMENTAL and runs the final full VACUUM. MaintenanceRepository exposes ReclaimFreePages(ctx, chunkPages), Checkpoint(ctx), Optimise and DatabaseStats; Vacuum is removed. The maintenance pass runs stats, a reclaim loop in chunks of 512 pages until the freelist is empty, optimise, a truncating checkpoint, stats, and records the existing size, freelist and ratio gauges.
  • A readings sampler on the reader pool runs at boot and after each cleanup pass, executing one grouped count by sensor, recording sqlite.readings.rows and holding the sample for the stats endpoint.
  • Ingest: one immediate transaction per batch; sensor and measurement-type repositories hold lower-cased name-to-id caches invalidated by their own write methods; one prepared insert; the threshold processor caches rules per sensor behind its mutex, invalidated by rule writes.
  • Auth: one read joining session, user and aggregated permissions on the reader; the last-accessed touch is a writer update only when older than 60 s.
  • Websockets: createPushWebSocket returns the connection; the hub gains Send(conn, v); the three connect handlers send their snapshot to the connecting socket only.
  • Client: WidgetDefinition.kind is required. WidgetFrame owns an IntersectionObserver with root margin 0px 0px 33% 0px and provides { visible, kind } by context, and sets data-widget-state. requestScheduler.schedule(priority, fn, { signal }) removes aborted waiters. useScheduledQuery(fetcher, { pollIntervalMs, deps }) implements held, queued, loading, fresh and error, registers with a single page-level poll clock, and pauses on document.visibilityState. PropertiesProvider and CurrentReadingsProvider own one reconnecting socket each. MeasurementTypesProvider loads both lists lazily through the scheduler. useLoaderVisibility gains showAfterMs = 100. The readings merge is one pass over a map with a fingerprint diff.
  • Bundle: react-query removed; the API docs route lazy-loaded.
  • Benchmark: ui/sensor_hub_ui/tests/first-load.spec.ts, chromium, Playwright webServer starting the built binary on a seeded temp database that serves the built SPA. A Go seed tool under the test harness writes five million readings over eight sensors, nine types and ninety days, keyed by a seed version for caching. A reference dashboard of twelve widgets taller than 1.33 viewports at 1280×800, including one toggle. A third CI job on pull request and push.

Integration points.

  • OpenAPI: GET /sensors/stats/total-readings response becomes { sampled_at: date-time, counts: { [sensor]: integer } }; the CLI and UI client are regenerated in the same slice. No other contract changes; has_readings keeps its name and meaning.
  • Application properties: database.reader.connections, integer, default 4, validated positive, advanced group, apply on restart.
  • Migrations 000021 (auto_vacuum switch and final VACUUM) and 000022 (join-table rebuild), both with down migrations.
  • Metrics: sqlite.readings.rows gauge; db_sql_* metrics gain a pool attribute.
  • CI: a first-load-benchmark job alongside unit-tests and integration-tests.

Security and privacy. No new endpoints or data. The reader pool is read-only at the SQLite level. Session validation is unchanged in what it checks and is never cached across requests. The observability token file is ignored by git as of the design commit and is not read by any code.

5. Risks

  • The final full VACUUM in migration 000021 pauses the Pi for roughly ten to fifteen seconds at the next startup, before the API listens. Mitigation: it runs once, at deploy, and is logged with its duration.
  • Migration 000022 scans readings once at startup on the Pi, in the region of ten seconds cold. Same mitigation.
  • The reader pool makes four slow reads at once the new way to stall the page. Mitigation: the query-plan tests and K3 and K4 in CI.
  • The join table now lags a new sensor by one message or collection interval before the dialog can configure it. Accepted in SQ4.
  • The scheduled-query hook touches every widget data path at once. Mitigation: it ships behind the existing widget tests, which mock the scheduler, and the benchmark asserts the whole page.
  • Counting statements through the instrumented driver for K5 couples a test to otelsql span names. Mitigation: the test counts through a driver hook owned by the test harness, not by span names.
  • The benchmark runs a browser and a seeded database in CI on every push, adding around two minutes. Accepted in SQ2; the seed is cached by version.
