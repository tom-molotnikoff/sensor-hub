Why controllable toggles take 1–2s to become usable

You asked me to investigate the WebSocket. The short version: the WebSocket is mostly innocent. It pushes the toggle's state the instant the connection registers. The 1–2s is a heavy SQLite query that produces that snapshot, queued behind the dashboard's chart-query burst.

Steps 8–9 (the shaded band) are the delay. Everything after is instant. The WebSocket "fires" correctly — it just has nothing to send until that contended query returns.

The critical path, in one function

sensor_hub/api/readings_api.go:69

func (s *Server) SubscribeCurrentReadings(c *gin.Context) {
    currentReadings, err := s.readingsService.ServiceGetLatest(ctx)  // heavy query, runs BEFORE upgrade
    ...
    createPushWebSocket(c, "current-readings")          // upgrade + register
    ws.BroadcastToTopic("current-readings", currentReadings) // pushed immediately
}

ServiceGetLatest is a ROW_NUMBER() OVER (PARTITION BY sensor_id, measurement_type_id ...) window scan over the whole readings table (db/readings_repository.go:193). Cheap when idle; serialized behind chart reads on the Pi's single-writer SQLite under load. And because it runs before the upgrade, it delays both the connection opening and the data.

Why the request scheduler didn't fix it

Structural miss #1

The snapshot rides the WebSocket, not REST

The scheduler only meters read-only REST calls. The toggle's state arrives over /readings/ws/current, which the scheduler never touches. So the one path that matters for the toggle was never governed.

Structural miss #2

The query still contends in SQLite

Capping REST to 4 concurrent reduced the flood from "unbounded" to "throttled" — a real win — but ServiceGetLatest still competes for the same single-threaded DB, and still runs before the upgrade. The critical path was never on the table the scheduler controls.

Net: the scheduler was a reasonable instinct (contention is the root cause) aimed one layer too high. It made commands more responsive once issued, but couldn't make the initial snapshot fast.

How to fix it

You chose server-confirmed state only — no optimistic last-known render. So the fix must make the real snapshot fast, not paper over it. That points hard at one approach.

A · In-memory "latest readings" store, served on connect

Recommended

Keep an in-process map sensorName → measurementType → Reading, updated every time a reading flows through (collection, command result). On WS connect, build the snapshot from memory instead of ServiceGetLatest — a microsecond read that never touches SQLite. Seed it once at startup from the existing query.

  • Removes the toggle's critical-path query from SQLite entirely — immune to the chart burst by construction, not by throttling.
  • Natural home: wrap "update the store + broadcast" into one Publish(readings) call so the cache and the live stream can never drift. (Today there are 3 broadcast sites that would each update it.)
  • Memory cost is trivial: bounded by #sensors × #measurement-types, last-value-wins.
Robustness HighLatency win ~1–2s → ~0Effort MediumTouches Go backend

B · Upgrade first, then fetch

Partial

Reorder the handler: register the connection before running the query, then push when it returns. The socket opens instantly; the data still waits on the contended query.

Cheap and correct, but alone it only fixes "connection opens late," not "controls usable late." Good as a companion to A, weak on its own.

C · Make the query cheap

Weaker

Add a covering index / dedicated latest-state table so ServiceGetLatest is fast. Reduces cost, but still hits SQLite and still serializes behind writes under load.

Strictly dominated by A: more DB-coupling for less isolation.

D · Throttle charts harder

More of the same

Lower REST concurrency, defer chart loads until controls resolve, or finally use the unused high tier. Trades chart speed for control speed and stays on the REST layer.

This is the road the scheduler already started down. Diminishing returns.

+ Secondary · the auth gate

Follow-up

Both sockets are gated on enabled: user != null, so they can't open until GET /auth/me resolves. That's a smaller, serial add-on to the delay — worth a look, but not the 1–2s.

Pipeline & index audit — what I actually found

I measured your live Pi and mapped every hot query against the existing indexes. The surprising result: the readings table isn't missing its key index — it already has the perfect one, but the chart query is written so SQLite can't reach it. Adding indexes is mostly the wrong move; one is redundant and actively slowing your writes.

Finding 1 — the composite index exists but is unreachable

Biggest win

You already have idx_readings_sensor_type_time (sensor_id, measurement_type_id, time DESC) — exactly the right shape. But the chart query filters by name, after the join, so SQLite can never use it:

Today — index unusable 
-- range-scans ALL sensors in the window,
-- then discards by name
WHERE r.time BETWEEN ? AND ?
  AND LOWER(s.name) = LOWER(?)
  AND LOWER(mt.name) = LOWER(?)
ORDER BY r.time ASC
Rewrite — composite kicks in 
-- resolve name -> id first (tiny lookups),
-- then a tight indexed range scan
WHERE r.sensor_id = ?
  AND r.measurement_type_id = ?
  AND r.time BETWEEN ? AND ?
ORDER BY r.time

A chart for office-plug power currently scans a time-slice across every sensor (including that 161k stream) and throws most of it away. Filtering by id lets the composite jump straight to the rows. Same fix applies to the aggregation window query (readings_repository.go:144), which partitions by s.name, mt.name too.

Finding 2 — drop a redundant index

Cheap win

idx_readings_sensor_id (sensor_id) is fully covered by the leftmost column of the composite. It buys nothing on reads and adds write cost to every insert — worst on the office-plug hot path.

Dropping it speeds ingest, which is part of the very contention causing the toggle delay. Reads + writes both win.

Finding 3 — verify the ASC time index

Confirm first

idx_readings_time_asc (time ASC) (migration 16) overlaps idx_readings_time (time DESC) — SQLite can usually walk a DESC index backwards for ASC order. Likely a second redundant index.

I'd confirm with EXPLAIN QUERY PLAN on the live DB before dropping — not assume.

The synergy: Finding 1 makes chart reads cheaper, Finding 2 makes ingest writes cheaper. Both shrink the SQLite contention window — the same root cause behind the toggle delay. The in-memory store (A) removes the toggle from that window entirely; the pipeline work shrinks the window for everything else.

Final plan

Scope settled. One cohesive change, two reinforcing workstreams. Query rewrite is in scope; index hygiene = drop redundant + verify-then-drop ASC; audit limited to the readings pipeline.

Workstream 1 · Toggle first-load

Go backend
  • A — in-memory store. Authoritative sensorName → type → Reading map, last-write-wins. Connect-snapshot reads from memory, not ServiceGetLatest. Seed once from the existing query at startup.
  • Single Publish(readings) that updates the store and broadcasts, so cache and live stream can't drift. Route the 3 existing broadcast sites (sensor_service.go:298/358/635) + the snapshot handler through it.
  • B — reorder. Upgrade/register before producing the snapshot in readings_api.go:69.
  • Frontend unchanged; server-confirmed-only preserved.

Workstream 2 · Readings pipeline

SQL + migration
  • F1 — rewrite by id. Resolve name→id up front, filter r.sensor_id = ? AND r.measurement_type_id = ? AND r.time BETWEEN ? in raw + aggregated + last + window queries. Unlocks the composite index.
  • F2 — drop idx_readings_sensor_id (redundant; cuts insert cost).
  • F3 — verify EXPLAIN QUERY PLAN, then drop idx_readings_time_asc if confirmed redundant.
  • New migration 000020 for the index drops; rewrite is code-only.
Out of scope: the WebSocket auth gate (enabled: user != null → /auth/me) and index audits of non-readings tables. Validate: first-load time-to-interactive before/after on the live Pi, EXPLAIN QUERY PLAN on rewritten queries, and the integration suite (go test -tags integration ./integration/) — keeping live-Pi load conservative.
