Sensor Hub · the design

Properties page: definitions, honest apply-states, one grouped page

Every decision from the interview is locked. This is the design itself - architecture, data flow, error handling, testing - plus two bugs I hit while tracing the data flow that this design has to answer for. Three questions left at the bottom.

The shape of it

Backend

  • Six new struct tags on ApplicationConfiguration: desc, group, unit, enum, apply, readonly.
  • PropertyDef and buildRegistry() carry them through - the reflection loop already exists, this is six more field.Tag.Get calls.
  • New GET /properties/definitions, spec-first in api/openapi.yaml, x-required-permission: view_properties.
  • GET /properties and PATCH /properties untouched. CLI and the retention cards keep working.
  • Sensitive-key plumbing deleted.
  • Two live-apply fixes: slog.LevelVar for the log level, and an interval function on periodic.TaskConfig.

Frontend

  • useProperties unchanged - it stays the websocket-backed value feed for everyone.
  • New usePropertyDefinitions - one fetch, cached for the session, definitions don't change without a deploy.
  • PropertiesCard is replaced by a page composed of PropertyGroupSection and one PropertyField per property, which picks its control from Kind, enum and readonly.
  • Rail with scroll-spy plus a search box filtering on key, label and description.
  • A property with a definition but no group, or a value with no definition, still renders - see the degradation rules below.

The registry, extended

Nothing here is a new mechanism - buildRegistry() already reflects over the struct at init(). These are additional tags on the same pass. 

type PropertyDef struct {
    // ... existing: FieldName, FieldIndex, Key, Kind, Default, File, Validate
    Description string       // desc  - one sentence, shown under the label
    Group       string       // group - sensors|retention|security|mqtt|email|weather|advanced
    Unit        string       // unit  - "seconds", "days", "hours"; suffix on the input
    Enum        []string     // enum  - comma-separated in the tag; renders a select
    Apply       ApplyState   // apply - live|next-cycle|action:<id>   (default: live)
    ReadOnly    bool         // readonly
}

Why apply defaults to live

18 of 29 properties are already live, so the default should be the common case and the tag should only appear where something is unusual. It also means the failure mode of forgetting the tag is "we claimed live and it was live" for most new properties - and the test below catches the rest.

Why Validate stays a string

Tempting to redesign it into min/max while we're here. Out of scope - the existing positive / non_negative / non_empty vocabulary is enough to drive client-side validation, and widening it is a separate change with its own risks.

Groups are returned as their own ordered list rather than inferred from the properties, so ordering and group descriptions live in the backend too and the UI holds no hardcoded knowledge of what a group is. label is derived from the field name if no tag overrides it, so no property can ship without a human-readable name.

Two bugs the data flow exposed

Neither is caused by this work. Both sit directly in its path, and per the engineering standards we fix what we find.

Bug 1 A broadcast wipes your in-progress edits

PropertiesCard does useEffect(() => { if (properties) setEditedProperties(properties) }, [properties]). Every websocket message is a fresh object identity, so every broadcast overwrites local state. If another admin saves - or you save in a second tab - everything you were half-way through typing is silently replaced. On a page where you might be editing several fields before saving, that is much worse than it is today.

Design answer: hold two maps - server values from the websocket, and a sparse map of only the fields you have touched. Render edited[key] ?? server[key]. A broadcast then updates untouched fields freely and leaves your edits alone. Where a broadcast changes a field you are editing, the helper line changes to say someone else changed this to X - reset to take theirs.

PropertiesCard.tsx:19-21

Bug 2 Editing the file over SSH doesn't reach the UI

The watcher detects an external file change and calls ReloadConfig, but never calls ws.BroadcastToTopic("properties", ...). So an SSH edit - or an RPM upgrade rewriting the defaults - updates the running config while every open browser keeps showing stale values until someone reloads the page. On a page that is about to display "saved value" and "modified from default", stale server state is actively misleading.

Design answer: broadcast after a successful watcher reload. One call, same as the service already does after a PATCH.

Degradation rules

The two sources can disagree. They must never produce a blank page.

SituationBehaviour
A value has no definitionRender it in an "Ungrouped" section as a plain text field with its raw key. Can only happen if the registry and the running config disagree, which shouldn't occur - but a silently missing property is worse than an ugly one.
A definition has no valueRender with the default as placeholder. Shouldn't happen - ConvertToMaps emits every registered key.
A definition has an unknown groupFalls into "Ungrouped" rather than vanishing.
The definitions request failsFall back to today's behaviour: flat list of key and text field, with a banner saying descriptions and typed controls are unavailable. The page still edits properties. This is the important one - a definitions outage must not take away the ability to fix your config.
The user lacks manage_propertiesEverything renders, all controls disabled, no Save button. Same as today.

Error handling

Client-side, before the PATCH

  • Type check from Kind: an int field rejects non-numeric input at the field.
  • Rule check from Validate: positive, non_negative, non_empty.
  • Save is disabled while any field is invalid, and the rail marks which groups hold errors - otherwise an invalid field in a scrolled-away group makes Save mysteriously dead.
  • Client validation is convenience only. The backend stays authoritative and the UI must handle a rejection it did not predict.

Server-side, on the PATCH

  • LoadConfigurationFromMaps already validates before anything is written, and the whole batch is rejected together. That is the right behaviour and it stays.
  • Today the error reaches the user as a raw Go string in a snackbar. The errors are already formatted as invalid <key> value: <raw>, so the API can return the offending key alongside the message and the UI can attach it to the right field.
  • Local edits survive a failed save. Currently a failure leaves you looking at an error with no clear state; the two-map model means your edits are still there to correct.
  • The file write is already async and only logs on failure - so the UI can report success while the write fails. Out of scope to fix here, but noted as a follow-up: the save should surface a persistence failure.

Testing

Go

  • Registry completeness - table test asserting every registered property has a non-empty desc and a known group. This is the test that keeps the metadata honest as properties are added, and it is the reason the docs table can be deleted safely.
  • Enum validity - any enum tag must contain the field's default.
  • Apply-state validity - apply parses to a known state, and any action:<id> names an action the API actually implements.
  • Endpoint - handler test for shape and for the view_properties permission.
  • Live-apply fixes - a test that changing log.level through the service changes what the logger emits, and a periodic test that a task picks up a new interval on the next tick.
  • Integration - per CLAUDE.md, go test -tags integration ./integration/ after any Go change. integration/properties_test.go already exists to extend.

Frontend

  • PropertyField renders the right control per type, including read-only and enum.
  • The Bug 1 case explicitly: type into a field, deliver a websocket message, assert the edit survives and untouched fields update.
  • Definitions-fetch failure falls back to the flat editable list rather than an empty page.
  • Search matches on key, label and description, and the group counts follow the filter.
  • Permission gating: no manage_properties means disabled controls and no Save.
  • Existing PendingSensorsCard.test.tsx and friends set the pattern - Vitest with the same testing-library idiom.

What this is not

In

  • Registry tags, definitions endpoint, the rebuilt page.
  • Typed controls, descriptions, apply-state, modified marker and reset, inline validation, search.
  • log.level and periodic-interval live-apply fixes.
  • Delete the sensitive-key plumbing.
  • Bugs 1 and 2.
  • Remove the property table from the docs and point at the UI.

Out - raised as their own issues

  • Live-apply for readings.aggregation.* - needs its own thinking about re-tiering mid-flight.
  • Live-apply for oauth.token.refresh.interval.minutes.
  • Surfacing an async file-write failure to the user.
  • Dispersing groups into feature pages - the agreed later phase.
  • Any change to the validate vocabulary.

Three things I want you to decide

1. When someone else changes a field you're editing

Bug 1's design answer keeps your edits. The question is what happens on the field where you actually collide.

2. The MQTT broker action

The broker has Start(), Stop() and IsRunning() already, so bouncing it in-process is possible. Whether we should is your call - it disconnects every publishing sensor.

3. The docs table - you didn't come back on this

Your instruction was to drop it and point at the UI. My caveat was that the docs are the only place someone can see what's configurable before they install. I'll do whichever you say; I'm not deciding it quietly.
