Make the dashboard feel fast: controllable widgets first

When a dashboard opens, the controllable toggles should settle into the correct state and respond to taps as fast as possible - even while the read-only charts are still blank. This document proposes how, grounds it in the current code, weighs alternatives, and ends with decisions for you to make.

The symptom

On the Raspberry Pi + SQLite deployment, opening a dashboard to flip a single switch feels sluggish:

  • 1 Settle delay - the switch takes a few seconds to show the correct on/off position after load.
  • 2 Command lag - flipping the switch takes ~a second to take effect, and gets worse the more widgets are on the dashboard.

The "scales with widget count" clue is the key: this is resource contention, not a fixed cost.

Diagnosis

Browser is snappy; render is fine. The wait is the backend returning data.

Every read-only chart fires GET /readings/between on mount and again every 30s. N charts ⇒ a burst of heavy SQLite aggregation queries that the single-threaded-ish Pi serializes.

The toggle's data and command queue up behind that burst.

Measured • confirmed

We proved the bottleneck on the live Pi

Using the authenticated CLI against the real instance, we timed a small "probe" request (proxy for the toggle's snapshot + command) while idle, then again while 6 concurrent chart-style aggregation queries hammered the Pi - a simulated busy dashboard. Read-only, bounded, one-shot.

The probe recovered to baseline the instant the query burst drained - so this is pure contention, not a fixed cost. Metering concurrency (the proposed scheduler) is exactly the right lever. A single aggregated chart query also costs 0.7-1.1s on its own, so even a handful firing at once saturates the Pi.
Important reframe

"Controllable first" really means "read-only out of the way"

The natural framing is "send the controllable widget's request first." But the one controllable widget (sensor-toggle) makes no REST request to prioritize. It reads from two shared WebSockets and writes commands to a third endpoint:

/sensors/ws

Sensor list + capabilities = what makes a sensor controllable.

/readings/ws/current

Live current values = the toggle's on/off position (the "settle").

POST /sensors/{id}/command

The command itself (the "flip"). Already optimistic in the UI.

So the lever is not jumping a queue. It is throttling the read-only REST flood so the Pi keeps spare capacity to answer the WebSocket snapshot and the command POST quickly. We get the controllable widget fast by getting everything else out of its way.

Current behavior vs target behavior

Today

Thundering herd on load

  • • All widgets mount at once; every chart fires its request immediately.
  • • No concurrency limit - the Pi gets N+ heavy queries simultaneously.
  • • No ordering - the toggle's WS snapshot competes with chart aggregation.
  • • Background 30s polls keep firing; a command can land mid-burst.
  • • useReadingsData calls apiClient.GET directly in a useEffect.
Target

Metered, prioritized loading

  • • A small client scheduler caps how many requests hit the Pi at once.
  • • Controllable data is highest priority; read-only charts wait their turn.
  • • The Pi always has headroom, so the WS snapshot settles quickly.
  • • A command preempts background polls so the flip lands fast.
  • • Read-only widgets fetch through the scheduler, not directly.

Proposed approach: a small priority request scheduler

Introduce one focused module - a priority-aware concurrency limiter (a priority semaphore, ~a hundred lines, not a framework). Every read-only REST fetch goes through it. It admits at most N requests to the Pi at a time and always admits the highest-priority waiter next.

Mechanism 1

Concurrency cap

At most N REST requests in flight to the Pi (a tunable setting, default 4). Stops the thundering herd, leaving CPU/SQLite headroom for the WS snapshot and commands.

Mechanism 2

Priority ordering

When a slot frees, the scheduler runs the highest-priority waiter. Controllable-related work first, then visible charts, then background polls.

Mechanism 3

Command preemption

While a command POST is in flight, the scheduler stops admitting new low-priority polls, so the Pi drains and the flip confirms quickly.

Alternatives considered

A. Priority scheduler

Recommended

Central concurrency cap + priority + preempt.

Wins: fixes settle and command lag; scales as widgets are added; one clear home for priority.
Cost: route every read-only fetch through it (~4 call sites today).

B. Load-order only

Render controllable widgets first; delay/stagger read-only mounts a tick later.

Wins: tiny change; helps the settle.
Cost: does not fix steady-state command lag (30s polls still collide); ordering is implicit and fragile.

C. Request coalescing

Dedupe identical /readings/between queries so charts share one request.

Wins: cuts total load; good complement.
Cost: only helps when widgets overlap; no prioritization or preemption. Orthogonal - can add later.

A and C compose well; B is effectively a weaker subset of A. The recommendation is A, optionally folding in C as a later enhancement.

Risks & things to verify

Root cause confirmed (measured)

Backend contention is now proven on the live Pi: probe latency rose from ~23ms to 1.3-2.6s under chart load and recovered instantly. No longer a risk - it's the validated premise. Remaining tuning: pick the right cap against this same Pi.

Cap too low = sluggish charts

If the concurrency cap is too aggressive, read-only charts feel slow to fill in. The cap needs tuning against the real Pi (Decision 1).

Stale-response guards

useReadingsData already guards stale responses via requestIdRef. Queueing must not break that ordering or its cleanup on unmount.

Preempt starvation

Pausing low-priority polls during commands must be bounded (e.g. only for the in-flight command, with a timeout) so polls can't be starved indefinitely.
