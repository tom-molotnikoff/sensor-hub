Where I disagree before we start

"only used by this"

Not quite. mock-sensor.dockerfile is also built by the integration tests (testharness/containers.go:97 resolves ../docker_tests). Moving it is still right - the test path just has to move with it.

And two of the "dotted around" files aren't used by anything: ui/sensor_hub_ui/sensor-hub-ui.dockerfile (nginx production image) plus nginx/default.conf and nginx.conf are leftovers from before the UI was embedded in the Go binary (ccab49f). They should be deleted, not moved.

"no build cache"

There is a layer cache - the Dockerfiles defeat it. sensor-hub.dockerfile does COPY . ./ before go mod download and before installing air and dlv, so any source change re-downloads modules and recompiles both tools. The UI test image does COPY . . before npm install.

The deeper point: source is bind-mounted over /app anyway, so the images shouldn't contain source at all.

the slow part may not be the build

There's no .dockerignore, so the Go image's context is 744 MB - 665 MB of it ui/node_modules - shipped to the daemon on every build.

But Go's own compile cache lives inside the container and dies with it, so every recreate makes air do a cold debug compile of the whole dependency graph. If that's where your time goes, a persistent GOCACHE volume and Delve-off-by-default will matter more than any Dockerfile change.

R2-1 · Tilt or Compose Watch?Agreed

Disagreement first: Tilt wouldn't fix the missed reloads any better than Compose Watch does. They work the same way: watch files on the host, then copy the changed ones into the container, where air and Vite see an ordinary local write. So on the actual problem they're equal. They only differ in what else you get.

One fact that makes this more interesting: your Docker context is default, which is native Docker Engine on Fedora 44, not Docker Desktop. The usual cause of missed reloads (file events not crossing Desktop's VM boundary) doesn't apply to you, and I haven't found the real cause. Copying files in avoids the problem whatever the cause turns out to be, which is why I'd switch rather than chase it.

R2-2 · How the seed keeps a trailing window fullAgreed

Following your D4 note: the seed step runs on every up, not just the first. It has two jobs that behave differently.

  • Top-up: for each seeded series, write synthetic readings from max(newest reading, now − window) up to now. Because it always starts from the newest reading, running it again seconds later writes nothing - no duplicates (that becomes an acceptance criterion).
  • Only seeded sensors that still exist get topped up. Sensors you add yourself are never touched.

S4 · The seedAgreed

A one-shot Go program, devstack/seed, run by the seed service from the sensor-hub image with the shared Go cache volumes, against the sensor-hub-data volume, before the hub starts. Each run goes through these steps:

  1. Open and migrate the database with the app's own migration runner (database.RunMigrations), so the schema always matches the app.
  2. Entities, once only. If there's no devseed_metadata marker row, create the users, admin API key, sensors, measurement types, MQTT subscription, alert rules and dashboards, then write the marker. Everything goes through the service layer wherever a service exists (UserService, SensorService including ServiceApproveSensor, the dashboard, alert and MQTT services). The API key is printed to the seed logs.
  3. Top-up, every run. For every seeded sensor that still exists, write data from max(newest existing, now − 30 d) up to now: readings at 1-minute spacing, plus health history and alert history. These are backdated rows, which no service can write, so they use bulk SQL batches in the style of testharness/seed. Values follow the same ranges and random walk as the live mocks, so history and live data join up without a visible seam.
  4. Exit 0. Compose then starts the hub.
  • Shared helpers (D7): the "create a user / sensor / dashboard" helpers are pulled out of testharness/layout.go into a package with no build tag, taking services as parameters rather than *Env. The layout tests keep their own pinned data, and the dev seed has its own dataset.
  • Identity of MQTT sensors: they're created with the name and driver config that auto-discovery would give them, so the mock's messages land on the approved sensor rather than a new pending one. verify against drivers/zigbee2mqtt.go.
  • Dashboards are defined in Go as typed widget configs. A unit test checks that every widget type registered in the UI's WidgetRegistry appears in at least one seeded dashboard, so adding a widget without seeding it fails the test.
  • Error handling: any failure exits non-zero with the step and cause in the log, and the hub doesn't start - a half-seeded stack is worse than one that doesn't start. Entity creation and its marker are written in one transaction where the services allow it. Otherwise the marker is written last, and a rerun that finds entities already there by name skips them.
