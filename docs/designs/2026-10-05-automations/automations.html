Letting Sensor Hub act on its own

This is the record of the design interview. Every decision is shown with the option that was agreed, and round-by-round notes sit beside the decisions they changed. The original framing follows. You want users to define rules that drive actuators without a person pressing the switch. Time comes first (#462, a lights timer). Sensor readings follow (#463, a TRV that heats below 16 °C). Along the way you want to untangle the reading path so it reads as the pipeline it really is. This page shows what I found in the code, where I disagree with the plan, the decisions I need from you, and three prototypes of the editor. Annotate anything. Each decision has its own Queue button.

The ask, and where I push back

verified Steelman

Today the actuators are remote controls. A command only goes out when a person or an agent sends one. Sensor Hub already knows the time and the latest value of every sensor, and it can already address every writable property of every device. The missing piece is a user-defined rule: "when X, do these things". It needs to be general enough to cover a timer, a delayed off and a thermostat loop, and it should be built once. Feeding sensor triggers needs a single, explicit reading pipeline. That pipeline also fixes the duplication that has grown in the ingest code.

What would make this wrong: devices that are better automated at the edge, such as Zigbee bindings or a Home Assistant install. That does not fit Sensor Hub's mix, though: HTTP temperature sensors next to Zigbee actuators. Rules that span protocols can only live in the hub.

report Where I disagree, or the code disagrees

  1. There are three ingest paths, not two. The periodic collector calls ServiceCollectAndStoreAllSensorReadings, not ServiceCollectFromSensorByName. All three do the same job in a different order (table below).
  2. Agreed: Automation "Pipeline" is about to mean two things. If the reading path becomes an explicit pipeline, user rules called pipelines collide with it. I suggest automation for the user-facing concept (D2).
  3. The alert engine is the wrong model to copy for sensor triggers. Alerts are level-triggered: they re-fire on every reading once the rate limit lapses. Actuation has to fire on the crossing, or it sends a command on every reading and runs into the existing one-command-in-flight 429.
  4. A lights timer needs a wall clock, and the hub has none. Everything runs in UTC and there is no timezone setting. "19:00" would be 20:00 local for half the year (D6).
  5. Agreed: durable runs A delay makes a run long-lived. "On, wait 4 h, off" plus a restart mid-wait leaves the lights on for good, unless runs survive restarts (D8).
  6. Commands need a person. CommandService.Send rejects a nil actor (command_service.go:113). Automations need a system actor, and a guard so manage_automations cannot be used to sidestep control_sensors (D12).

Proposed shape

depends on D10, D11, D7

One reading pipeline that every ingest path hands its batch to. It stores the batch, then fans out to an ordered list of consumers. Automations become one more consumer, plus a scheduler for time. Both feed a single engine, which starts runs. A run executes its steps through the existing command service as a system actor.

Packages

readings/ (new): the pipeline and its consumer interface. automation/ (new): model, validation, scheduler, engine and executor. actuation/ stays as command lifecycle and gains Send for the system actor. Agreed You asked for new triggers to live in the actuation module. I would keep when (automation) apart from how a command travels (actuation), so each stays small.

The hot path stays hot

Consumers run synchronously except automations. The automation consumer only does a non-blocking send onto a buffered channel, and a single worker goroutine drains it. One worker keeps readings in order per sensor, which edge detection needs. A goroutine per reading would let a 15.9 arrive after a 16.1.

Loops

An automation's own command echoes back as a reading, which can trigger another automation, and so on. Each run records its cause chain, and the engine refuses a run whose cause chain is already 5 or more runs long [assumption].

What we call the user-facing thing

Agreed - Automation
Agreed: "Automation". The user-facing concept is an automation, made of triggers and steps. Each execution is a run. "Pipeline" is reserved for the internal reading pipeline. Original reasoning: Home Assistant and most smart-home tools already use it for "when X, do Y", so users will recognise it. It also leaves "pipeline" free for the reading pipeline, which is the internal concept you want to make explicit.

Agreed - A

D6

Whose clock "19:00" is

Agreed - A

Today there is no hub timezone. Storage, drivers and the command tracker are all UTC, and the UI renders in the browser's zone. A daily trigger has to be computed in a real zone, or it moves by an hour across BST.

Recommend A. Add a hub-wide hub.timezone property (an IANA name such as Europe/London), editable on the Properties page. Next-fire times are computed in that zone and stored in UTC. DST rule: a skipped local time (01:30 on the spring-forward night) fires at the next valid minute. A repeated local time (01:30 on the fall-back night) fires once.
Your note, answered. You asked whether BST is handled automatically. Yes. You set hub.timezone = Europe/London once. Go's timezone database knows the UK rules, so 19:00 stays 19:00 local through every clock change with nothing to maintain. Two safeguards: the binary embeds time/tzdata, so a container without /usr/share/zoneinfo still has the rules. And if the hub zone is UTC while your browser is in a different zone, the Automations page shows a one-click "Use Europe/London" banner. [assumption] on the banner.
Queued ✓

Execution

D7

How time triggers get evaluated - you asked "periodic again, or something better?"

Agreed - A
Recommend A, a next-fire scheduler. Keep each automation's next fire time in a min-heap and sleep on a single time.Timer until the earliest one. When it fires, start the run, compute that automation's next fire and re-arm. Editing an automation, or changing the timezone, wakes the loop to recompute. Durable waits use the same heap, since a waiting run is just one more "wake me at T". The loop runs under the same supervision as periodic.RunTask (panic recovery, backoff). No dependency is needed: computing next fire for time-of-day + weekdays is about 30 lines with time.Date.
Queued ✓
D8

What happens across a restart

Durable runs agreedAgreed - durable + grace window
Agreed: runs are stored in the database. Every run is a row, and so is every step outcome. A waiting run stores resume_at, and on startup the scheduler reloads every running or waiting run and carries on from its current step. A restart mid-wait no longer strands a device.

Agreed: a trigger that came due while the hub was down fires on startup only if it is inside the grace window.

Recommend A. A missed schedule fires once on startup if it is less than a grace window late (default 10 min, a property). Anything older is recorded as a missed run and not fired, because turning the lights on at 07:00 for a 19:00 trigger is worse than skipping it.

D9

When a sensor trigger fires (#463, decided now so #462 does not paint it into a corner)

Agreed - A, with noise handling (D15)
Recommend A, which is edge-triggered. The trigger fires when the condition goes from false to true: 16.2 → 15.8 fires, and 15.8 → 15.6 does not. The engine keeps the last truth value per trigger in memory. After a restart or an edit, the first reading counts as a crossing if the condition already holds. That way the house converges, and the heating comes on after a restart in a cold room.
What would make A wrong: a sensor that chatters across the threshold, such as a door contact or a noisy temperature at exactly 16.0. A hysteresis band, or "must hold for N seconds", would then become a must-have rather than a later addition.
Your note, answered. You asked me to check real noise before trusting crossings. I did, and a bare crossing is not enough: see the noise evidence and D15.

D10

Shape of the reading pipeline

Agreed - A
Recommend A. A readings.Pipeline has one Process(ctx, sensor, readings) entry point. It ingests, sets health on failure, drops unknown types, then calls an ordered list of Consumer interfaces registered in cmd/serve.go. All three ingest paths call it. The order is explicit and the same everywhere, and adding automations is one line of wiring. SetReadingsObserver and the three copies of the alert loop go away.

D11

How readings reach the automation engine

Agreed - A
Recommend A, which is what you leaned towards: an immediate, in-process handoff, with a goroutine keeping it off the MQTT path. The detail that matters is a single worker draining a buffered channel, which preserves order. If the buffer fills, the newest reading replaces the oldest for that series and a dropped-readings counter goes up. Edge detection only needs the latest value per series.

What your sensors' noise actually looks like

Raw readings from home.sensor-hub, 28 Sep - 5 Oct 2026, read-only. For every threshold across each sensor's range (0.5 °C or 1 %RH apart), I replayed the week and counted crossings. A crossing that reverses within 15 minutes is chatter, and each one would be a wasted command.

What this says: a bare crossing would toggle the Living Room TRV up to 7 times in an hour. A small re-arm margin fixes temperature completely at no cost in latency. A hold time on its own is both slower and leakier. For binary sensors, what matters is ignoring repeated values; a crossing-based engine does that for free, where a level-based one would fire on every heartbeat.

D15

How sensor triggers handle noise

Agreed - per trigger
Recommend A. Every numeric trigger has a re-arm margin. "Falls below 16 °C" fires at 15.9 and cannot fire again until the value has reached 16.0 + margin. The margin is prefilled from the measurement type (temperature 0.3 °C, humidity 2 %RH, from the data above with some headroom) and can be edited per trigger. Any trigger can also set an optional "for at least" hold time, which defaults to 0. It is useful on door contacts if those sub-5 s states turn out to be bounces. The defaults live as a new column on measurement_types, seeded by migration. (Dropped, see your note below.)
What would make A wrong: a measurement type whose noise is nothing like these, such as power on the office plug, which jumps by watts. A type default would then mislead more than help, and the margin should be required with no default for those types.
Your note, answered. You want this defined per automation and not baked around today's sensors. Agreed: margin (numeric triggers) and "for at least" hold (any trigger) are fields on each trigger. There are no type defaults and no new measurement_types column. How the form fills the margin field is D20.

Round 3 - statuses, and what they exposed

all agreed

You asked what makes an automation "completed", since it is always waiting for its next run. The prototype was mixing two different things: the automation, which is long-lived and usually just armed, and a run, which has a beginning and an end. Separating them raises three questions that had been hiding behind the mix-up.

D17

The status model

Agreed - A
Recommend A, as drawn above. An automation is Off, Armed (enabled and waiting for a trigger, which is its normal state), Running (it has a run that is running or waiting), or Broken (it references a sensor or capability that no longer exists, so it cannot fire). A failed last run shows as a red flag next to Armed until a run succeeds. It is not a state of its own, because the automation is still armed. Each run ends as succeeded, failed or cancelled. It is recorded as missed or skipped if it never started. "Completed" is gone. The list prototype now uses this model.
Queued ✓
D18

A trigger fires while a run is still going

Agreed - A

"Evening lights" is 2 hours into its 4-hour wait and another trigger fires. A motion trigger would make this routine. The engine has to do something definite.

Recommend A, a per-automation mode with two values. Single is the default: while a run is active, new triggers are recorded as skipped. Restart cancels the active run and starts a new one, which is the "motion extends the light timer" behaviour. Home Assistant also has queued and parallel modes; I would leave them out until something needs them.
Queued ✓
D19

Editing or disabling an automation mid-run

Agreed - A

This is the stranded-device problem again. If saving or switching off "Evening lights" during its wait cancelled the run, the lamp would stay on.

Recommend A. A run copies its steps when it starts, so an edit applies from the next run and the current one finishes as it was defined. Switching an automation off stops new triggers but lets an active run finish. The editor shows an explicit Cancel run button beside an active run, for when you really do want it stopped.
Queued ✓
D20

The margin field, now that it is per automation

Agreed - A

Agreed in D15: margin and hold are set on each trigger, and nothing is baked in from today's sensors. Your goal is a general system that just works. The risk is a user who leaves the margin at 0 and gets a TRV toggling 7 times an hour. That does not just work either.

Recommend A. The margin is required, and the form suggests a value worked out from the chosen series' own recent behaviour: the 95th percentile of reading-to-reading change over the last 24 h, rounded up to the sensor's step. The suggestion uses the same rule for any sensor and any measurement type, including ones that do not exist yet, and nothing is hard-coded. You can accept it or type your own, and the stored value is always the one on the trigger.
Your note. "Use the sensor data to be smarter." The suggestion is computed server-side from the chosen series' recent readings, so the CLI and agents can use it as well as the form. The exact endpoint shape is left to the spec [assumption].
Queued ✓
